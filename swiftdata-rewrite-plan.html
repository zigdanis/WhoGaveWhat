SwiftData rewrite plan

Replace Core Data completely, improve the app’s domain model while compatibility is irrelevant, and deliver the result as a reviewed pull request with no migration machinery.

TLDR: Start from current master, model every gift as an explicit giver → recipient relationship, unify household members and contacts into one role-aware person type, keep SwiftData behind the existing gateways, remove every Core Data artifact, and add in-memory persistence coverage. There will be no migration plan, importer, or legacy-store cleanup path.

Context

The current app isolates persistence behind GiftGateway and PeopleGateway, while SwiftUI reads plain value snapshots from AppData. That boundary is worth preserving: views should not gain @Query, ModelContext, or direct @Model dependencies as part of this rewrite.

The current Core Data schema assumes each gift always pairs one household member with one external person. The UI is more flexible: any tracked person can be the giver or recipient. This is the central schema mismatch to fix while the app has no published data to preserve.

Constraints

  • No migration: no SchemaMigrationPlan, Core Data importer, old-store reader, compatibility shim, or cleanup routine.
  • Fresh namespace: use a distinctly named SwiftData configuration so existing development Core Data files are never interpreted as SwiftData.
  • Stable app boundary: SwiftData storage objects remain private to persistence adapters; features and use cases continue using plain domain values.
  • Stable identity: person and gift IDs must survive edits and remain suitable for SwiftUI lists and navigation.
  • Tooling: all Xcode, test, Simulator, accessibility, and screenshot work goes through the repository-pinned XcodeBuildMCP CLI.
  • Delivery: implement on a branch based on freshly fetched origin/master, open a PR in English, respond to review bots, and continue until required checks are green.

SwiftData records

StoredPerson stores a unique stable ID, name, color, role, sort index, gifts given, and gifts received. StoredGift stores a unique stable ID, content fields, occasion, event date, creation date, value/payment metadata, and required giver/recipient relationships.

Use explicit inverse relationships. Person deletion must remove every gift involving that person. Prefer modeled cascade behavior when SwiftData accepts the dual inverse schema cleanly; otherwise perform an explicit same-context delete of involving gifts before deleting the person, covered by an integration test.

GiftDirection should not be the source of truth in storage. Resolve it from the endpoints and current household roles so it cannot drift from the actual relationship.

Architecture

  1. SwiftDataStore owns one Schema, named ModelConfiguration, ModelContainer, and main-actor ModelContext.
  2. SwiftDataGiftGateway and SwiftDataPeopleGateway perform fetch, mapping, save, and delete operations.
  3. Gateways map storage records to framework-independent Gift and Person values.
  4. Use cases preserve validation and business logic; SaveGiftUseCase assigns UUID-backed IDs and preserves createdAt during edits.
  5. AppData continues publishing value snapshots to SwiftUI, with narrow household/contact projections and stable list identity.

Fresh-install behavior: the production store creates only the required “You” household anchor. Sample data is limited to preview/test stores; it is not silently inserted into a real user store.

Work plan

  1. Fetch origin/master, verify a clean worktree, and create feature/swiftdata from the fetched commit.
  2. Reshape domain values first: unified people, endpoint-based gifts, occasion naming, explicit creation order, and centralized direction resolution.
  3. Add the SwiftData schema and store with a fresh configuration name and in-memory/seed modes.
  4. Replace Core Data gateways with SwiftData gateways while preserving protocol boundaries.
  5. Update app composition, use cases, app state, and feature call sites.
  6. Delete all Core Data source, managed-object definitions, and the entire .xcdatamodeld bundle.
  7. Update test support and add persistence integration tests.
  8. Run static cleanup checks, full build/tests, and the affected app scenario on the preferred Simulator.
  9. Open the PR, process automated and human review, push fixes, and repeat checks until green.

Risks

  • Relationship rules: dual giver/recipient inverses and cascade deletion must be exercised by a real in-memory ModelContainer.
  • Edit ordering: an edit must retain the original createdAt, or same-day gifts will jump unexpectedly.
  • Direction edge cases: household-to-household and contact-to-contact gifts need a documented deterministic fallback.
  • Fresh-store startup: app composition must load the “You” anchor before pickers and onboarding flows rely on it.
  • Delete atomicity: deleting involving gifts and the person should occur in one context transaction/save.
  • Environment gap: Linux can run repository/static checks and invoke the CLI, but Xcode compilation and Simulator verification require a macOS runner.

Verification

Persistence tests

  • Fresh production-style store contains only “You”; preview/test seed has 12 gifts, 4 household people, and 6 contacts.
  • Gift insert, reload, update without duplication, delete, and createdAt preservation.
  • Person create, role mapping, rename, reload, and deletion.
  • Deleting a person removes gifts where they are either giver or recipient while preserving unrelated gifts.
  • Separate in-memory stores are isolated and use the new configuration namespace.

Static checks

  • git diff --check
  • No imports or symbols for Core Data, managed objects, old endpoint names, or old domain type names.
  • No .xcdatamodeld, migration plan, importer, old-store reader, or cleanup code remains.

Xcode and UI

  • Use XcodeBuildMCP to discover the project/scheme and an already-running compatible Simulator; otherwise prefer iPhone 17 Pro.
  • Run the complete test suite and a clean build/build-and-run.
  • Walk onboarding into the app, add received and given gifts, edit a gift, inspect details, rename a person, and delete a person.
  • Capture a fresh accessibility snapshot and screenshot, then inspect layout, clipping, overlap, contrast, and readability.
  • Watch PR checks and review bots, address actionable findings, and continue until required checks are green.

Verification needed on macOS: this workspace is currently on Linux, where XcodeBuildMCP can be installed and invoked but reports spawn xcodebuild ENOENT. Compilation, tests, and Simulator evidence must therefore come from the macOS CI/review runner.
