Clean Architecture для WhoGaveWhat

Практичный микс Clean Architecture, структуры Mythia и feature-first организации SwiftUI — без TCA, без общего бизнес-комбайна и без лишнего числа targets.

Кратко: отказаться от широкого AppStore. Навигацию оставить в узком AppRouter, UI сгруппировать в Features, бизнес-сценарии назвать и вынести в UseCases, внешние способы хранения и AI — в Gateways, а техническую основу SDK — в Infrastructure. Core Data остаётся только временной реализацией gateway; переход на SwiftData выполняется отдельным PR.

Контекст

Сейчас 13 SwiftUI-файлов находятся в общей папке Views, а AppStore.swift на 658 строк совмещает навигацию, состояние форм, форматирование, расчёты, Core Data-запросы и бизнес-действия. Название Store обычно означает единый источник состояния в Redux/Elm/TCA-подобном подходе. Здесь нет reducer/action-модели, поэтому название скрывает смешение ответственностей вместо того, чтобы объяснять их.

В Mythia верхнеуровневые Screens, UseCases, Gateways, Helpers и Environment делают роли файлов визуально понятными. Для WhoGaveWhat берём эту читаемость, заменяем Screens на более подходящее SwiftUI-имя Features, а Environment — на Infrastructure.

Xcode-проект использует file-system-synchronized groups, поэтому физические папки автоматически отобразятся в Xcode.

Исправленные решения

  • AppStore исчезает. Глобальная UI-навигация получает точное имя AppRouter. Состояние формы и экрана остаётся внутри соответствующей feature. Бизнес-действия выполняют use cases.
  • Ports исчезает. Это термин hexagonal architecture для интерфейсов на границе приложения, но без контекста он здесь только мешает. Используем знакомое по Mythia слово Gateways.
  • GiftRepository переименовывается в GiftGateway. Речь была не о Git-репозитории, а об абстракции хранилища подарков. Новое имя меньше провоцирует такую неоднозначность.
  • GiftParsing переименовывается в GiftIntelligenceGateway. Это граница к Apple Foundation Models для получения emoji и оценки цены, а не общий parser.
  • GiftRules.swift исчезает. Валидация черновика относится к модели черновика или save-use-case; сортировка — к Gift; аналитические расчёты — к insights-use-case. Общего файла «правила подарка» не будет.
  • PostHog не относится к gift gateways. В WhoGaveWhat сейчас нет PostHog. Если аналитика появится, это будет отдельный AnalyticsGateway с реализацией PostHogAnalyticsGateway; заранее пустую абстракцию не создаём.

Colors.swift — безопасное имя: имя Swift-файла не создаёт символ или namespace и не конфликтует с типом Color. Внутри можно использовать простые семантические цвета через extension Color либо отдельный AppColors, если понадобится namespace.

Helpers не должен становиться свалкой: там только маленькие технические extensions и форматирование, используемые несколькими фичами. Бизнес-решения остаются в моделях и use cases.

Границы слоёв

СлойОтветственностьЧего в нём нет
AppComposition root и глобальная навигация. Создаёт gateways и use cases, передаёт их фичам.Бизнес-правил, запросов Core Data и экранной разметки.
FeaturesSwiftUI views, локальное UI-состояние и feature-specific helpers/subviews.Прямых Core Data/Foundation Models вызовов.
ModelsЧистые сущности предметной области. Например, Gift знает свои данные и естественные инварианты.Color, SwiftUI, Core Data managed objects и навигации.
UseCasesЗаконченные пользовательские бизнес-действия: загрузить, сохранить, удалить, рассчитать.SwiftUI и деталей конкретной базы/AI SDK.
GatewaysКонтракты к внешнему миру и их адаптеры: persistence, Foundation Models, UserDefaults.UI-состояния и решений о показе экранов.
InfrastructureНизкоуровневая техническая основа SDK: Core Data stack, managed models и конфигурация.Use-case логики.
DesignSystemЦвета, тема, переиспользуемые визуальные примитивы и layouts.Компонентов, которые сами обращаются к gateway/use case.

Направление вызовов: Feature → UseCase → Gateway → Infrastructure/SDK. Модели передаются между ними как чистые значения. AppComposition — единственное место, которое знает конкретные реализации.

Показ экрана не является бизнес-use-case: это ответственность AppRouter. Use case отвечает на намерение пользователя вроде «сохранить подарок» или «загрузить подарки человека», а router решает, какой SwiftUI view открыть.

Пример потока данных

Сохранение подарка проходит по одной читаемой цепочке:

AddGiftSheet
  → SaveGiftUseCase
      1. проверяет AddGiftDraft
      2. определяет GiftFlow
      3. создаёт или обновляет Gift
  → GiftGateway.save(gift)
  → CoreDataGiftGateway
  → CoreDataStack

AI-подсказка отделена от сохранения: SuggestGiftUseCase сначала обращается к GiftIntelligenceGateway, затем применяет локальный fallback. Apple Foundation Models остаётся деталью FoundationModelsGiftIntelligenceGateway.

SwiftData — отдельный следующий PR

Этот PR не меняет persistence engine: миграция Core Data → SwiftData одновременно со структурным рефакторингом слишком усложнит проверку и откат. Но новая граница специально готовит замену.

В следующем PR CoreDataGiftGateway, CoreDataPeopleGateway и CoreDataStack будут заменены SwiftData-реализациями. Features, UseCases и чистые Models при этом не должны измениться. Отдельно потребуется решить стратегию миграции уже сохранённых данных.

План работ

  1. Зафиксировать baseline. Запустить текущие unit tests и simulator build до переноса.
  2. Механически разложить UI. Перенести экраны в Features без изменения поведения. Разделить общие визуальные примитивы и feature-specific views.
  3. Собрать Design System. Разделить текущий Theme.swift на Colors.swift и остальные theme tokens; разнести общие компоненты по понятным файлам.
  4. Выделить чистые модели. Убрать из Gift, Person и household-моделей SwiftUI/Core Data зависимости. Переместить цветовые представления в presentation/design-system слой.
  5. Ввести gateways вокруг текущих интеграций. Сначала обернуть существующие Core Data, Foundation Models и UserDefaults реализации без смены технологий.
  6. Извлечь use cases из AppStore. Переносить по одному сценарию вместе с существующими тестами: load/save/delete gifts, people actions, suggestions, insights и onboarding.
  7. Удалить остаток AppStore. Навигационную часть заменить узким AppRouter, состояния форм вернуть соответствующим features, затем удалить файл целиком.
  8. Собрать зависимости. Создать concrete gateways и use cases в AppComposition; не добавлять DI-фреймворк.
  9. Обновить тесты и README. Сгруппировать тесты по use cases/gateways и описать реальное направление зависимостей.
  10. Проверить итог. Полный test suite, чистая build и smoke test основных маршрутов.

Проверка

  • xcodebuild test на доступном iOS Simulator с CODE_SIGNING_ALLOWED=NO.
  • Чистая сборка app target после всех перемещений.
  • Проверка, что Xcode видит новую иерархию папок и в target не появились пропавшие или дублирующиеся исходники.
  • Smoke test: onboarding/sign-in, вкладки Home/People/Insights, добавление и редактирование подарка, удаление подарка/человека, Settings.
  • Тесты use cases используют test gateways, а Core Data gateway проверяется отдельно на in-memory stack.
  • Проверка git diff: первый коммит содержит только актуальную версию этого плана.

Риски и защита от них

  • Use-case explosion. Не создавать класс на каждый getter или кнопку. Отдельный use case нужен для законченного бизнес-сценария, который можно назвать глаголом и проверить отдельно.
  • Gateway как новое имя для свалки. Gateway существует только для внешней системы или долговременного хранилища. Чистые расчёты туда не попадают.
  • Слишком большой рефакторинг. Перенос UI, gateways, use cases и удаление store выполняются отдельными логическими коммитами со сборкой между ними.
  • Смешение со SwiftData. В этом PR сохраняется Core Data и текущая схема данных; SwiftData выносится в отдельный PR с собственной миграционной проверкой.
  • Скрытая MVVM-архитектура. Не создавать ViewModel на каждый экран автоматически. Feature-specific state появляется только там, где SwiftUI view действительно не может удобно владеть состоянием сама.
