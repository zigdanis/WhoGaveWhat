One Xcode execution path

Revised implementation plan for agent-driven building, testing, Simulator interaction, accessibility inspection, screenshots, and visual verification in WhoGaveWhat.

TLDR: use the official XcodeBuildMCP CLI and its official CLI skill as the only execution system. Remove the OpenAI build-ios-apps plugin, its XcodeBuildMCP MCP launcher, and all nine bundled skills. Keep the two existing Apple-authored SwiftUI knowledge skills because they provide API guidance but cannot build, test, or control a Simulator. Add one project config, one operating guide, and unambiguous AGENTS.md rules in a separate PR.

Final architecture

One execution authority: the xcodebuildmcp CLI executable.

The agent will learn that executable through exactly one project-local skill: .agents/skills/xcodebuildmcp-cli/SKILL.md. There will be no XcodeBuildMCP MCP server, no OpenAI iOS execution plugin, and no second wrapper around xcodebuild or simctl.

Project defaults.xcodebuildmcp/config.yamlStore WhoGaveWhat project, scheme, and preferred Simulator defaults.

No MCP: XcodeBuildMCP product version 2.x is not the new MCP protocol generation sometimes called “MCP v2.” This plan therefore does not launch XcodeBuildMCP as an MCP server and does not depend on that protocol question.

Which skills are valuable, and which are redundant?

The useful distinction is not “OpenAI skill versus XcodeBuildMCP skill.” It is execution versus domain knowledge.

  • An execution skill tells the agent how to operate a command-line tool. Two execution skills for the same job create ambiguity. WhoGaveWhat should have exactly one: xcodebuildmcp-cli.
  • A domain knowledge skill supplies authoritative SwiftUI rules when relevant. It cannot run the app and therefore does not compete with the CLI.

Do not add enabledWorkflows: that setting controls MCP tool exposure, while the CLI exposes its command groups directly. Avoiding it makes the CLI-only architecture explicit.

How the agent will use the single tool

  1. Read the project-local xcodebuildmcp-cli skill when a task requires an Xcode build, test, launch, Simulator, log, debug, accessibility, or screenshot operation.
  2. Run xcodebuildmcp --help, then the relevant subgroup’s --help when exact flags are uncertain. Do not guess command syntax.
  3. Discover or reuse a booted Simulator. If an iPhone 17 Pro is already booted, bind all operations to it. Otherwise prefer iPhone 17 Pro.
  4. Use the CLI’s combined build-and-run command when the intent is to launch the app. Use its test command when the intent is verification.
  5. Before interacting, collect an accessibility hierarchy and target stable identifiers or labels. Coordinates are a documented last resort.
  6. After UI-affecting work, walk the complete modified scenario, collect a fresh accessibility hierarchy, take a screenshot, open the image, and make an explicit visual judgment.
  7. Use structured json or jsonl output where supported so the agent can reliably parse results.

Required AGENTS.md contract

The PR will add concise rules with the following meaning:

  • Mandatory route: use the xcodebuildmcp CLI for all build, test, install, launch, Simulator interaction, accessibility inspection, logging, debugging, and screenshot work.
  • No MCP route: do not configure or call XcodeBuildMCP as an MCP server.
  • No silent fallback: do not use raw xcodebuild, xcrun, or simctl for those operations. If the CLI itself is broken or lacks a required capability, stop, report the exact limitation, and ask Danis before adopting a second route.
  • Help first: inspect CLI and subgroup help instead of inventing flags.
  • Simulator reuse: reuse an already-running compatible iPhone Simulator; prefer iPhone 17 Pro and keep one UDID for the entire task.
  • Proof: report selected project, scheme, Simulator name/UDID, build result, exact test totals, and fallback status.
  • UI verification: after UI changes, walk the modified scenario, inspect the accessibility hierarchy, capture a screenshot, open it, and explicitly check state, spacing, clipping, overlap, contrast, and readability.
  • Artifacts: keep screenshots, logs, DerivedData, and machine-specific output outside tracked source paths unless the task explicitly requests committed artifacts.

Implementation steps after explicit approval

  1. Create isolation: refresh master, verify the existing worktree, and create a dedicated branch such as codex/xcodebuildmcp-cli-integration. Preserve and exclude unrelated changes.
  2. Pin the input: recheck the latest stable XcodeBuildMCP release on implementation day. Use one exact reviewed version everywhere; never use @latest. Version 2.7.0 was selected after that check.
  3. Install the executable: run npm install --global xcodebuildmcp@2.7.0. Verify command -v xcodebuildmcp, xcodebuildmcp --version, and xcodebuildmcp tools --json. Record the resolved path and npm global prefix in the setup evidence. Do not commit a binary or node_modules.
  4. Capture the official skill safely: use the installed release’s init --skill cli capability in a temporary directory, inspect its complete output, and add only the official xcodebuildmcp-cli skill under .agents/skills/. Do not install the MCP skill.
  5. Remove the competing source: delete plugins/build-ios-apps/, .agents/plugins/marketplace.json, and the now-empty .codex/config.toml. Confirm no remaining file starts XcodeBuildMCP with mcp or references build-ios-apps.
  6. Add project defaults: add .xcodebuildmcp/config.yaml with the project, scheme, iPhone 17 Pro preference, and telemetry disabled. Validate against the pinned release.
  7. Add durable documentation: create docs/xcodebuildmcp.md containing the exact version, installation method, resolved executable path check, official skill provenance, verified commands, update procedure, and recovery steps.
  8. Update agent policy: extend AGENTS.md with the contract above while preserving all existing project rules.
  9. Reload and inspect discovery: start a fresh agent session. Confirm the CLI skill is discovered, the two Apple knowledge skills remain, and neither the OpenAI plugin nor XcodeBuildMCP MCP tools are present.
  10. Run acceptance checks: execute the matrix below using the already-booted compatible Simulator when available.
  11. Review and deliver: inspect all staged paths and the complete diff, run review before any push, then create a separate ready-for-review PR with English GitHub text. Do not merge without instruction.

Separate PR boundary

Included: removing the OpenAI plugin and its enablement; adding the official CLI skill; adding project configuration and documentation; extending AGENTS.md; and evidence from the acceptance checks.

Excluded: application source changes, Xcode project changes, feature work, UI changes, CI changes, global Codex configuration, committed binaries, committed screenshots, Simulator reset/erase, and installation of optional profiling or domain skills.

The PR title, commits, description, review comments, and evidence will be written in English. Installation changes on the developer machine will be documented but cannot themselves be represented by the Git diff.

Approval gate: this file is the only deliverable now. Do not install the CLI, generate a skill, delete the existing plugin, edit configuration, create a branch, commit, push, or open a PR until Danis explicitly approves this revised plan.
