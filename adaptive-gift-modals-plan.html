Adaptive Gift Modals

Implementation plan for intrinsically sized Add Gift and calendar sheets, deterministic selection of newly created people, and removal of nonfunctional Settings placeholders.

TLDR: Replace greedy navigation-container sheet roots and measured detents with a reusable intrinsic modal scaffold plus .presentationSizing(.fitted). Route both existing-person taps and newly created people through the same endpoint-specific selection callback, and leave Settings with only Currency and Third-party licenses.

Context

The current AddGiftSheet combines a NavigationStack, a geometry-measured compact detent, and a large detent. Keyboard presentation can promote it to the large detent. Picker sheets also use a navigation container; despite the calendar’s own intrinsic measurement and fitted sizing, the container accepts excess height and leaves the calendar visually centered inside empty space.

Person creation already tries to select the result, but endpoint dispatch is duplicated behind a boolean and lacks acceptance coverage. Settings mixes two functional destinations with local-only toggles, empty actions, static rows, and a hardcoded version that does not match the project setting.

Goal

  • Select a newly added person automatically for the exact From or To field that launched creation.
  • Make the calendar sheet bottom-attached and only as tall as its intrinsic content.
  • Let Add Gift resize around its content and keyboard without expanding to full-screen height.
  • Remove every nonfunctional Settings option.

Constraints

  • The feature branch starts from fetched origin/master.
  • The iOS 26 deployment target supports fitted presentation sizing.
  • Long content, edit mode, Dynamic Type, and keyboard-visible states must remain scrollable.
  • UI verification must use XcodeBuildMCP, reuse an already-running simulator, and prefer iPhone 17 Pro otherwise.
  • All GitHub-facing text must be English.

Options Considered

Intrinsic scaffold plus fitted sheet — selected

A non-greedy VStack-based modal scaffold reports its ideal size while an internal scroll view handles genuine overflow. This follows content, Details expansion, and the keyboard without keyboard notifications or fixed-height calculations.

Geometry-measured custom detents — rejected

The current approach is self-referential: container and keyboard changes influence the measured height and the system can still promote the presentation to its large detent.

Forced popover or inline overlay — rejected

Compact-width popover adaptation changes anchoring and dismissal semantics, while a custom overlay would recreate presentation, keyboard, and accessibility behavior already handled by native sheets.

A UIKit custom presentation controller with preferredContentSize remains a fallback only if runtime testing shows fitted sizing is defective.

Proposed Approach

  1. Add a small reusable modal header/scaffold with intrinsic vertical layout, optional leading action, and narrowly scoped inputs.
  2. Restructure AddGiftSheet.swift around that scaffold. Remove custom detent state and geometry measurement, retain overflow scrolling and focus dismissal, and apply .presentationSizing(.fitted).
  3. Move picker presentation into a dedicated AddGiftPickerSheet.swift. Use the same scaffold for the calendar and avoid any spacer or max-height root. Keep existing detents for genuinely long list pickers unless runtime behavior supports fitting them too.
  4. Change person creation to return an ID and pass that ID through the same onSelection callback used by existing rows. The parent supplies selectFrom or selectTo, eliminating boolean endpoint dispatch.
  5. Simplify SettingsView.swift to Currency and Third-party licenses only. Remove profile, Notifications, Default view, iCloud sync, Export, Rate, Privacy Policy, Version, Sign out, and all now-unused state/helpers.

Work Plan

  1. Add focused state/callback tests for new-person selection in both From and To flows, including duplicate-name reuse.
  2. Implement the reusable modal scaffold and migrate Add Gift without changing its save/focus semantics.
  3. Migrate picker composition, preserve list picker behavior, and make the calendar’s intrinsic size determine its sheet height.
  4. Remove Settings placeholders and dead supporting code.
  5. Build and run tests, then walk all modified UI scenarios and capture screenshots.
  6. Submit a draft PR, obtain independent review, correct every blocker in focused commits, then monitor CI and review feedback until green.

Risks

  • A six-row calendar month may change UICalendarView height; navigation between short and long months must invalidate fitted sizing correctly.
  • Expanded Details, larger Dynamic Type, or edit mode may exceed available height; the scaffold must compress the scroll region, not clip content.
  • Removing Version follows the strict placeholder interpretation because it is hardcoded, mismatched, and presented with an action chevron.

Verification

  • Run the complete test suite and build through XcodeBuildMCP.
  • Verify Add Gift with the name keyboard, expanded Details, value keyboard, and dismissed keyboard.
  • Add a new From person and a separate new To person; confirm each underlying field updates automatically.
  • Open Date, confirm no large blank region, and navigate across four-, five-, and six-row months.
  • Open Settings, confirm placeholders are absent, and verify Currency and licenses still navigate.
  • Capture and visually inspect snapshots for the modified scenarios.
